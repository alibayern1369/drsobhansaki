# راهنمای مدیر

## اجرای محلی

نسخهٔ Node.js ۲۴ یا جدیدتر نصب باشد. `npm ci` و سپس `npm run dev` را اجرا کنید. نشانی اصلی `/fa` و انگلیسی `/en` است. `npm run build` نسخهٔ تولیدی را می‌سازد.

`.env.example` را به `.env.local` کپی کنید. هیچ کلید واقعی را در Git یا پیام عمومی قرار ندهید. مقدار `AUTH_SECRET` باید حداقل ۳۲ کاراکتر تصادفی داشته باشد.

## پایگاه داده

با حساب مجاز Neon وارد شوید. قبل از تغییر schema، یک branch توسعهٔ جدا ایجاد و connection string همان branch را در فایل محیط قرار دهید. `DATABASE_URL` برای برنامه و `DATABASE_URL_UNPOOLED` مستقیم برای migration است. `npm run db:generate` فایل SQL تولید می‌کند؛ قبل از `npm run db:migrate` SQL و branch مقصد را بررسی کنید. از push یا reset روی production استفاده نکنید.

برای داده‌های اولیه فقط روی branch توسعه، `ALLOW_DEV_SEED=true` و `NEON_BRANCH=development` قرار دهید و `npm run db:seed` را اجرا کنید. رزرو و خدمات به‌طور پیش‌فرض غیرفعال‌اند و همهٔ مقاله‌ها پیش‌نویس می‌مانند. seed دوباره‌اجراشدنی است و محتوای موجود را بازنویسی نمی‌کند.

## ورود

بیمار از `/fa/login` با شماره همراه وارد می‌شود. برای آزمایش محلی، `SMS_PROVIDER=development` و `DEV_OTP_CODE` شش‌رقمی تعیین کنید. این حالت در production فعال نمی‌شود. کد در خروجی چاپ نمی‌شود.

مدیر از `/fa/admin` با نام کاربری و رمز جدا وارد می‌شود؛ هدر و فوتر عمومی در پنل نمایش داده نمی‌شوند. در «امنیت و ورود» رمز را تغییر دهید و در صورت نیاز پیامک یا Google Authenticator را با تأیید کد فعال کنید. تأیید دومرحله‌ای ۱۵ دقیقه اعتبار دارد. مدیر کل از «کاربران و نقش‌ها» می‌تواند برای پزشک و کارکنان نام کاربری و رمز جدا بسازد؛ رمز فعلی مدیر کل برای این کار لازم است. تغییر نقش و غیرفعال‌سازی، نشست‌های کاربر را لغو می‌کند و تغییر نقش خود مدیر از این فرم ممنوع است.

## مدیریت روزمرهٔ پنل

- «تصاویر و هویت بصری»: عکس پزشک، مشاوره، خدمات پزشکی، لوگو، آیکون‌های مرورگر و عکس اشتراک‌گذاری را از دستگاه انتخاب کنید؛ پیش‌نمایش را بررسی و «ذخیره تغییرات» را بزنید. JPG، PNG و WebP تا ۴ مگابایت پذیرفته می‌شوند. تصاویر این بخش عمومی هستند و از فضای نام جدا از رسیدهای خصوصی خوانده می‌شوند. آپلود به `BLOB_READ_WRITE_TOKEN` سروری نیاز دارد؛ هیچ توکنی به مرورگر داده نمی‌شود.
- «محتوای سایت»: زبان را انتخاب کنید، متن‌ها را ویرایش و گزینهٔ انتشار همان زبان را تنظیم کنید. هر زبان جدا ذخیره می‌شود. متن‌های عمومی، معرفی پزشک، منو و فوتر از محتوای منتشرشده خوانده می‌شوند.
- «اطلاعات تماس»: شماره، ایمیل، نشانی، ساعات پاسخ‌گویی، تحصیلات، شماره نظام پزشکی و زمینه‌های مشاوره را وارد کنید. «حریم خصوصی و شرایط» متن سیاست‌ها را برای هر زبان تنظیم می‌کند. «SEO» عنوان و توضیح جستجو را تنظیم می‌کند. هیچ‌کدام به ویرایش JSON نیاز ندارند.
- «حساب‌های بانکی»: نام بانک، صاحب کارت، شماره کارت و ترتیب نمایش را وارد کنید. ارقام فارسی/عربی و فاصله یا خط تیره پذیرفته و به شماره استاندارد تبدیل می‌شوند. برای نمایش در پرداخت جدید، حساب را فعال کنید. حساب قبلی را به‌جای حذف تاریخچه، غیرفعال کنید.
- «تقویم»: زمان تکی یا مجموعهٔ زمان‌های یک روز را بسازید؛ مجموعه بر اساس مدت مشاوره و فاصلهٔ بین نوبت‌ها ایجاد می‌شود. ساعت‌ها تهران هستند. تعطیلی را ثبت یا حذف و زمان‌ها را فعال/غیرفعال کنید.
- «درخواست‌های بیماران»: پس از انجام لغو یا جابه‌جایی در بخش نوبت‌ها، درخواست را رسیدگی‌شده یا ردشده علامت بزنید. بستن درخواست به‌تنهایی وضعیت نوبت را تغییر نمی‌دهد.
- «مقالات»: مقاله را به‌صورت پیش‌نویس اضافه یا ویرایش کنید. انتشار هر زبان نیازمند تأیید علمی همان متن است؛ توقف انتشار نیز در دسترس است. مقاله‌های تأییدشده در صفحهٔ اصلی و مجله نمایش داده می‌شوند.
- «مدیریت پیامک»: با انتخاب رویداد، قالب ذخیره‌شده برای ویرایش بارگذاری می‌شود. گزارش تحویل و تلاش مجدد پیام‌های ناموفق هم در همین بخش است.
- «گزارش امنیتی» و فعالیت‌های اخیر به‌صورت جدول و متن خوانا نمایش داده می‌شوند. گزینهٔ خروج از حساب و لینک مشاهدهٔ سایت در منوی پنل قرار دارند.

## اتصال ملی‌پیامک

بررسی این مرحله: build، TypeScript و lint موفق؛ ۵۴ آزمون کد موفق و ۳ آزمون وابسته به تنظیمات جدا skip شدند. هشت آزمون مرورگر شامل گردش همهٔ منوهای واقعی، نبود هدر/فوتر عمومی در ادمین، حفظ منوی صفحات عمومی، نمایش موبایل و ارسال دادهٔ فرم‌ها موفق شدند. آزمون ارسال فرم و انتخاب عکس در مرورگر با پاسخ کنترل‌شده اجرا می‌شود تا محتوای واقعی سایت تغییر نکند.

برای ارسال OTP با خط خدماتی اشتراکی، `SMS_PROVIDER=melipayamak` و متغیرهای سروری `MELIPAYAMAK_USERNAME`، `MELIPAYAMAK_PASSWORD` و `MELIPAYAMAK_OTP_BODY_ID` لازم‌اند. رمز، مقدار مجاز وب‌سرویس در حساب شماست؛ آن را در چت یا Git قرار ندهید. الگوی تأییدشده باید فقط یک متغیر برای کد ورود داشته باشد. برنامه کد را با متد `BaseServiceNumber` ارسال می‌کند. برای پیام‌های غیر OTP، خط ارسال `MELIPAYAMAK_FROM` نیز لازم است؛ نبود خط باعث تأیید کاذب ارسال اعلان نمی‌شود.

روش اتصال مطابق [نمونهٔ رسمی REST ملی‌پیامک](https://github.com/Melipayamak/melipayamak-node/blob/master/src/sms/rest.js) است. پاسخ HTTP 200 به‌تنهایی موفقیت نیست؛ وضعیت پاسخ و شناسهٔ مثبت ارسال نیز بررسی می‌شوند. آزمون adapter بدون ارسال واقعی انجام شده و ارسال واقعی تا تنظیم credentials آزموده نشده است. متغیرهای ورسل پس از ذخیره نیاز به deployment تازه دارند. `ADMIN_TOTP_SECRETS` باید با UUID مدیر در همان دیتابیس مقصد تطبیق داشته باشد؛ تنظیم development به‌تنهایی Production را تنظیم نمی‌کند.

## رزرو و پرداخت

تعرفه‌ها در پنل به ریال ثبت می‌شوند؛ مبلغ رزروهای قبلی با تغییر تعرفه عوض نمی‌شود. پیام‌رسان‌ها جداگانه فعال می‌شوند. فعال‌سازی رزرو در تنظیمات، پس از تأیید اطلاعات بانکی و زمان‌ها انجام شود. کارت آزمایشی در سایت وجود ندارد.

رسید پرداخت اثبات واریز نیست. قبل از تأیید در پنل، واریز را مستقلاً در حساب بانکی بررسی کنید. تأیید پرداخت بدون زمان، نوبت را در انتظار زمان‌بندی قرار می‌دهد. SMS از outbox ارسال می‌شود؛ خطای پیامک تغییر نوبت را برنمی‌گرداند.

## محتوا

متن صفحهٔ اصلی با کلید `homepage` و زبان `fa` یا `en` مدیریت می‌شود. تغییرات تا `published=true` عمومی نمی‌شوند. متن پزشکی و ترجمه باید جداگانه بررسی شوند. ثبت مقاله، پیش‌نویس ایجاد می‌کند و API تأیید تنها برای پزشک و مدیر کل دارای MFA است.

## پیش از انتشار

فهرست کارهای باقی‌مانده در IMPLEMENTATION-STATUS.fa.md باید بررسی شود. اطلاعات تماس، مدارک، عکس، بانک، سیاست لغو و حریم خصوصی را تأیید کنید. آزمون‌های کامل سرویس‌های واقعی روی محیط توسعه، تعیین محل داده و بررسی حقوقی هنوز لازم‌اند.
# ذخیره‌سازی خصوصی رسید

در تب ذخیره‌سازی رسید، مدت نگهداری، برآورد حجم رسیدهای ثبت‌شده، آخرین اجرای Cron و خطاهای حذف نمایش داده می‌شود. پزشک یا مدیر مجاز با MFA تازه می‌تواند پیش‌نمایش dry-run بگیرد. تصویب سیاست و تغییر مدت الزامی فقط برای super_admin و پس از تأیید صریح بررسی الزامات است. پیش‌نمایش هرگز فایل حذف نمی‌کند.

در جزئیات رسید، اختلاف پرداخت، نگهداری دستی، نگهداری حقوقی و تاریخ الزام قابل ثبت است. رسید در حال بررسی، اختلاف‌دار یا مشمول نگهداری حذف نمی‌شود. تصویب سیاست به‌تنهایی حذف را فعال نمی‌کند؛ متغیر سروری `RECEIPT_CLEANUP_ALLOW_DELETE` نیز باید پس از اجازهٔ صریح فعال شود. اکنون false است. تأیید واریز همچنان اقدام مستقل مدیر است.
